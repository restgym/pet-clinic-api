# Specifications of Spring PetClinic REST

## Original specification

`original/pet-clinic-openapi.yaml` (OpenAPI 3.0.1, YAML), unchanged.

- **Made by**: written by hand by Spring PetClinic developers.
- **Source**: https://github.com/spring-petclinic/spring-petclinic-rest/blob/8409c0a7361a56b5526ae2fd2f60f723c6e3d30a/src/main/resources/openapi.yml

The project is API-first: its code is generated from this file (openapi-generator, `generatorName: spring`, `interfaceOnly: true`). Its server is `http://localhost:9966/petclinic/api`, the port and the context path of the configuration of the API (`server.port=9966`, `server.servlet.context-path=/petclinic/`; RESTgym runs it on 8080). At runtime, the API also serves a specification generated by springdoc from the code (OpenAPI 3.1.0, at `/petclinic/v3/api-docs`, checked 2026-10), which is not the original: it has the base path `/api` in the paths, a server URL written from the request, the same 34 operations of the original but `GET /oops`, 5 more operations on `/` (`redirectToSwagger`), and no schema `VetFields`.

## Standardized specification

`standardized/pet-clinic-openapi.yaml`: the original with the change below. `standardized/pet-clinic-openapi.json` is the same specification in JSON, converted with yq 4.44.3 (the same content and order of properties, checked; see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). The Swagger 2.0 version is converted from it (see below).

Changes from the original:

- **Server `http://localhost:8080`, and base path `/petclinic/api` moved into the paths**: the server is `http://localhost:8080` instead of `http://localhost:9966/petclinic/api`, and each path starts with `/petclinic/api` (e.g., `/petclinic/api/owners` instead of `/owners`; all 17 paths). So the URLs of the operations are those of the API in its RESTgym container (e.g., `http://localhost:8080/petclinic/api/owners`).
  - **Port**: 8080, the port of the API in its RESTgym container (`entrypoint.sh` starts it with `-Dserver.port=8080`), instead of 9966, the port of the configuration of the API (`server.port=9966` in `application.properties`). The context path of the configuration (`/petclinic/`) is kept by RESTgym, so the base path is the same. The tools reach the API through the proxy of RESTgym, and replace the host and the port.
  - **Base path**: in each path for the tools that do not handle base paths.

**Swagger 2.0 version** (`standardized/pet-clinic-swagger.json`, and `standardized/pet-clinic-swagger.yaml`, the same in YAML): converted from `standardized/pet-clinic-openapi.json` with hidi 3.10.2, the command-line tool of Microsoft's OpenAPI.NET (`mcr.microsoft.com/openapi/hidi:3.10.2.202608213`, `hidi transform -v 2.0 -f json`); its output is only formatted with yq 4.44.3, and its YAML version is converted with yq (see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). Checked against the OpenAPI 3 version: the same 35 operations, with the same parameters (name, location, required), request bodies and response codes, and the same 15 schemas, in the same order; it passes the official validation. What the conversion changes: the server becomes `host: localhost:8080` and `schemes: [http]` (no `basePath`, which means `/`); the schemas become `definitions`; the request bodies become `body` (or form) parameters, and the media types of the request bodies and responses become `consumes` and `produces`.

The official validation passes: `standardized/validation.json` (2026-10, swagger-validator-v2 2.1.9) has no messages.

## Corrected specification

`corrected/pet-clinic-openapi.yaml`: the standardized specification with the change below, which makes it match the implementation of the version packaged. The two files are identical except this change. `corrected/pet-clinic-openapi.json` is the same specification in JSON, converted with yq 4.44.3 (the same content and order of properties, checked; see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). The Swagger 2.0 version is converted from it (see below).

Changes from the standardized specification:

- **Operation `GET /petclinic/api/oops` removed** (the path with its only operation, `failingRequest`; 35 operations in the standardized specification, 34 in the corrected one). The specification documents it as "Always fails" ("Produces sample error response", with responses 200, 304, 400 and 500), but the API does not implement it: the executable has only the interface generated from the specification (`OopsApi`), and no controller that implements it, so no handler is mapped to the path. Verified at runtime (2026-10, in its RESTgym container, through the proxy): every request answers 500 `NoResourceFoundException: No static resource api/oops.`, the generic answer of the API to a path that nothing serves, not the sample error that the specification describes.
  - The tag `failing`, used only by this operation, is kept: no operation uses it anymore.
  - The path is still served as before (the behavior of the API is kept).

**Swagger 2.0 version** (`corrected/pet-clinic-swagger.json`, and `corrected/pet-clinic-swagger.yaml`, the same in YAML): converted from `corrected/pet-clinic-openapi.json` with hidi 3.10.2, the command-line tool of Microsoft's OpenAPI.NET (`mcr.microsoft.com/openapi/hidi:3.10.2.202608213`, `hidi transform -v 2.0 -f json`); its output is only formatted with yq 4.44.3, and its YAML version is converted with yq (see §6.4 of `docs/API-INTEGRATION-PROTOCOL.md` in RESTgym). Checked against the OpenAPI 3 version: the same 34 operations, with the same parameters (name, location, required), request bodies and response codes, and the same 15 schemas, in the same order; it passes the official validation. What the conversion changes: the server becomes `host: localhost:8080` and `schemes: [http]` (no `basePath`, which means `/`); the schemas become `definitions`; the request bodies become `body` (or form) parameters, and the media types of the request bodies and responses become `consumes` and `produces`.

The official validation passes: `corrected/validation.json` (2026-10, swagger-validator-v2 2.1.9) has no messages.

## Endpoints of the original that may interfere with authentication

RESTgym does not authenticate the requests to this API (it needs no authentication). The security of PetClinic is disabled in its default configuration (the one RESTgym runs), so no endpoint can change what the tools are allowed to do. If it were enabled, this endpoint would matter:

- `POST /users`: creates users of the security of PetClinic, with their roles.
